---
title: "Elicitation"
description: "Forward Codex user-input requests to ACP clients that support them."
---

Some Codex server requests need free-form input from the user mid-turn. The
adapter forwards these to the host as ACP elicitation requests — but only when
the client is able to answer them.

## When elicitation fires

During a turn, a Codex `app-server` request that requires user input is mapped
onto an ACP elicitation call to the client. The client's response is passed back
to Codex so the turn can continue. Native `item/tool/requestUserInput` requests
MUST carry the non-empty `turnId` of the currently active native turn. Missing,
stale, and post-turn requests receive an empty native answer without invoking
the client.

Codex only offers its clarifying-question tool (`item/tool/requestUserInput`)
when the session runs in plan collaboration mode; in the default mode the tool
is unavailable, so no clarifying question is raised (`TestCodexCLIClarifyingQuestionElicitation`
runs a plan-mode session to elicit one).

Codex also uses `mcpServer/elicitation/request` for MCP tool approval. The
hard-cutover native shape marks those requests with
`_meta.codex_approval_kind = "mcp_tool_call"` directly in the flattened `_meta`
object. They are permission requests, not user elicitations, and correlate
through the active tool ledger to the exact published nonterminal ACP tool-call
ID. Nested metadata shapes are rejected. Both approval and user
elicitation requests MUST carry the non-empty native `turnId` of the currently
active ACP turn. Missing, stale, or post-turn requests are cancelled locally
before any host callback or tool-ledger match.

The initialize response advertises route-envelope version 1 at
`_meta["acp-go.dev/route"].versions`. Every form and URL elicitation preserves
its native metadata and adds one complete reserved route object containing
`version`, logical `sessionId`, the prompt's `turnNonce`, and exactly one native
`toolCallId` or `requestId`. A native or MCP payload that already contains the
reserved key is rejected rather than overwritten or merged.

An MCP user elicitation that names a native `toolCallId` or `itemId` is
associated with a tool already published in the active turn. The adapter maps
that native identifier to the exact nonterminal ACP tool-call ID before issuing
the elicitation. Missing, completed, or ambiguous explicit associations are
cancelled; they are never forwarded with an invented tool identity. Native MCP
elicitation requests without an explicit tool identifier remain standalone,
even when Codex reports the active `turnId` and `serverName`: those fields do
not establish MCP tool-item ownership. Standalone requests use the native
JSON-RPC request ID, represented as a non-empty route string, or the URL-flow
elicitation ID as `requestId`. The adapter mints a random string correlation
when neither is usable. Numeric request-ID union values are never written to
the route, and null, empty, or multi-variant route values are rejected.

## Capability gating

Elicitation is gated on the capability the client advertised at initialize:

- If the client advertised elicitation support, the request is forwarded and the
  client's answer is returned to Codex.
- If the client did **not** advertise support, the adapter rejects the Codex
  server request outright rather than issuing an unsupported client call.

<Note>
  Because elicitation is capability-gated, a client that omits the elicitation
  capability will see affected Codex requests fail fast instead of hanging.
  Raw diagnostics for these requests are available through
  [`_codex/rawEvent`](/docs/features/raw-events) when the session opts in.
</Note>
