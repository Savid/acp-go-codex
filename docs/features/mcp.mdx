---
title: "MCP"
description: "Attach MCP servers to a session and set their tool trust level."
---

The adapter accepts MCP servers on a session and converts them into `codex
app-server` thread configuration. Two transports are supported: stdio and
streamable HTTP.

The adapter sends each session's servers only through
`thread/start.config.mcp_servers` and re-supplies the same config through
`thread/resume.config.mcp_servers`. It never converts session MCP into
process-global `-c mcp_servers.*` arguments. HTTP headers and stdio environment
values therefore stay inside the app-server JSON-RPC stream instead of process
arguments, the app-server environment, the workspace, or the rollout store.

## Configure MCP servers

Attach one or more servers when you build the session request. Use
`StdioMCPServer` for a locally launched process and `HTTPMCPServer` for a
streamable-HTTP endpoint:

```go
req := codexacp.NewSessionRequest("/workspace/project",
	codexacp.WithSessionMCPServers(
		codexacp.StdioMCPServer("tools", "node", []string{"server.js"}, nil),
		codexacp.HTTPMCPServer("remote", "https://mcp.example/v1", map[string]string{
			"Authorization": "Bearer token",
		}),
	),
	codexacp.WithSessionCodexOptions(codexacp.NewCodexOptions(
		codexacp.WithCodexMCPToolApprovalMode("approve"),
	)),
)
```

| Constructor | Transport | Arguments |
| --- | --- | --- |
| `StdioMCPServer` | stdio | name, command, args, env |
| `HTTPMCPServer` | streamable HTTP | name, url, headers |

## Tool approval

`mcpToolApprovalMode` sets the trust level applied to every MCP server in the
session. It accepts exactly `auto`, `prompt`, or `approve`, and maps to Codex's
`default_tools_approval_mode` config for each server — Codex owns what each value
does. Any other value is rejected with invalid params.

<Note>
  MCP server names must be non-empty, unique, and non-whitespace, and only stdio
  and streamable-HTTP transports are accepted. Any other transport is rejected
  with an invalid-params error at session start.
</Note>

After native-process replacement, every loaded thread is configured before any
thread runs its bounded `runtime_ready` canary. This ordering is required even
when two threads use the same MCP server name with different endpoints or
credentials.
