The adapter has two supported integration modes. Both expose the same ACP
method surface and start local Codex app-server sessions on demand.

## Standalone CLI

Run `acp-go-codex` as an ACP stdio subprocess:

```bash
acp-go-codex -codex /usr/local/bin/codex -model gpt-5.5
```

Useful flags:

| Flag | Purpose |
| --- | --- |
| `-codex` | Path to the Codex CLI. Defaults to `codex` on `PATH`. |
| `-codex-home` | `CODEX_HOME` for launched Codex processes. |
| `-model` | Default Codex model for new sessions. |
| `-enable-goals` | Enable Codex experimental native thread goal APIs. |
| `-debug` | Write adapter debug logs to stderr. |
| `-cli login` | Run a local Codex login command. |
| `-cli logout` | Run a local Codex logout command. |

ACP stdio uses stdout for JSON-RPC. Logs and diagnostics must go to stderr or a
separate telemetry backend.

## Embedded Go

Embed the same agent in a Go process:

```go
err := codexacp.Serve(ctx, input, output,
    codexacp.WithCodexPath("/usr/local/bin/codex"),
    codexacp.WithCodexHome("/tmp/codex-home"),
    codexacp.WithDefaultModel("gpt-5.5"),
)
```

Use this mode when your host already owns process lifetime, logging,
OpenTelemetry providers, auth refresh, or durable [SessionStore](/docs/features/session-store)
integration.

## Same ACP contract

Standalone and embedded modes share:

- the same [`initialize`](/docs/reference/acp-methods) capabilities;
- the same session lifecycle methods;
- the same permission, elicitation, MCP, raw-event, goal, and import
  extension behavior;
- the same update mapping from Codex app-server events.

The only difference is ownership. Standalone mode owns process flags and
environment. Embedded mode accepts Go options and caller-owned streams.

## MCP proxy subcommand

`acp-go-codex mcp-proxy` is an internal subcommand launched by the adapter when
it rewrites ACP-transport MCP servers into Codex stdio MCP config. Hosts should
not call it directly; configure MCP servers on session requests instead.
